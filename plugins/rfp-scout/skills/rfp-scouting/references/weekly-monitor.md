# 주간 공고 모니터링 — 실행 절차와 템플릿

주 1회 자동 실행되는 IRIS 중심 공고 모니터링의 상세 절차(실행 요일·시각은 설치 시 지정).
`rfp-scouting` SKILL.md 7절에서 참조한다.

## 목차
1. 실행 절차 (7단계)
2. RFP 관련성 판정 기준
3. 분석리포트 템플릿
4. HTML 결과 리포트
5. 알림·메일 템플릿
6. 상태 파일 스키마
7. 자동 실행 설정
8. 실패 모드

## 1. 실행 절차

```
① 프로파일 로드      profile.md (연구주제 서술·키워드·알림설정)
② IRIS 신규 수집     지난 실행 이후 게시분 — iris_fetch.py list
③ 기보고 제외        seen_rfp.json 대조
④ 하드필터          마감 경과·주관자격 미달·규모/기간 하한·제외어
⑤ 첨부 RFP 심층대조  다운로드 → 텍스트추출 → 항목분할 → 3등급 판정
⑥ 히트 시 산출       분석리포트 → HTML 리포트 → 알림 → 메일 초안
⑦ 이력 갱신          seen_rfp.json + 최종 탐색 시각
```

**⑤가 이 모니터링의 존재 이유다.** 제목만 보는 알림은 RSS 구독으로 충분하며, 자동화의 가치가 없다.

**하드필터로 탈락한 건도 첨부를 열어 확인 사살하는 편이 낫다.** 규모 미달로 걸러진 공고에
정말 내 주제가 없었는지까지 확인해 두면, 다음 회차에 같은 공고를 두고 다시 고민하지 않는다.
확인 결과는 이력의 `note`에 남긴다.

## 2. RFP 관련성 판정 기준

프로파일의 **연구주제 서술**과 RFP 항목을 의미 대조한다. 키워드 문자열 일치가 아니다.

| 등급 | 판단 기준 | 예 (예시 프로파일: 산업용 열교환기·폐열회수) |
|------|----------|--------------------------------------------|
| **직접관련** | RFP 핵심 요구기술 = 내 주력. 주관/핵심역할 수행 가능 | "150℃급 산업 폐열회수 열교환기 고효율화" |
| **간접관련** | 세부과제·위탁·공동연구로 참여 여지. 인접 기술 or 내 기술이 부품으로 들어감 | "산업 공정 폐열 회수 시스템 실증" (열교환기가 구성요소) |
| **무관** | 접점 없음 | "수소 저장용 소재 개발" |

**판정 규칙**
- 애매하면 **간접관련로 올린다.** 누락(false negative)이 오탐보다 비싸다 — 놓친 공고는 다음 해까지 기다려야 한다.
- 판정마다 **RFP 원문 문장을 그대로 인용**한다. 인용 없는 판정은 검증 불가이며 환각 위험이 있다.
- RFP 문서를 열지 못했으면 등급 뒤에 `(잠정 — RFP 원문 미확인)`을 붙인다. 확인한 척하지 않는다.
- 연구축 어휘가 첨부 전문에서 **0건**이면 그 사실 자체를 근거로 적는다("5개 연구축 어휘 0건").

## 3. 분석리포트 템플릿

경로: `reports/{YYYYMMDD}_{공고약칭}.md`

```markdown
## STATUS: OK | PARTIAL
# [직접관련] 2027년도 ○○기술개발사업 신규지원 대상과제 공고

| 항목 | 내용 |
|------|------|
| 공고ID | IRIS 0XXXXX ([원문](https://www.iris.go.kr/contents/retrieveBsnsAncmView.do?ancmId=0XXXXX)) |
| 공고기관 / 전문기관 | ○○부 / ○○원 |
| 접수기간 | 2026-08-10 ~ 2026-09-15 (**D-43**) |
| 총 규모 / 과제당 | 1,200억 / 연 10억 내외 |
| 주관 자격 | 제한 없음 (기업 참여 필수) |
| 로컬 사본 | `raw/20260810_○○기술_공고.pdf` (+ 첨부 3건) |

## 1. 관련 RFP (원문 인용)
> **[과제번호 2027-XX-03] ○○ 고효율화**
> "…조건에서 … 체적 30% 저감 및 성능 20% 향상을 목표로 …"

## 2. 내 연구주제와의 접점
- 직접 대응: (보유 역량·실적을 근거와 함께)
- 차별화 가능 지점:
- 부족한 부분: (솔직하게 — 컨소시엄·장비·실적 갭)

## 3. 자격·컨소시엄 요건
## 4. 준비 일정 (D-43 기준 역산)
## 5. 판정
**추천 / 보류** — 근거 3줄. 보류면 무엇이 해소되면 추천으로 바뀌는지 명시.

## 6. 같은 공고의 기타 RFP (간접관련)
| 과제번호 | 과제명 | 등급 | 사유 |
```

리포트는 **사용자가 3분 안에 "낼지 말지"를 판단할 수 있어야** 한다. 원문 복사·붙여넣기 나열은 리포트가 아니다.

## 4. HTML 결과 리포트

사람이 먼저 보는 산출물은 `result/latest.html` 한 파일이다. 마크다운 후보 목록은 그 원본 데이터다.

- **히트 0건인 주에도 반드시 만든다.** "이번 주 해당 없음"과 탐색 범위·탈락 사유가 적힌 리포트가
  나와야 모니터링이 실제로 돌았다는 증거가 된다. 파일이 그대로면 실행이 죽은 것과 구분되지 않는다.
- **자기완결 단일 파일**로 만든다 — CSS·폰트를 파일 안에 넣고 외부 요청을 0으로 둔다. 그래야
  오프라인에서 열리고 메일에 첨부해도 서체가 유지된다. 라이트/다크 토글을 붙이면 야간 확인이 편하다.
- **직전 회차 HTML을 구조 템플릿으로 재사용**하고 수치·문구만 갈아끼운다. 매주 새로 디자인하지 않는다.
- 새 파일을 쓰기 전에 기존 `latest.html`을 `archive/{직전회차YYYYMMDD}.html`로 옮긴다.
- 공고를 언급하는 모든 자리에 원문 링크(`portal-sources.md` §2)를 걸고, `raw/`에 받아 둔 첨부는
  로컬 파일 링크도 함께 단다(한글·공백은 percent-encoding). `<a>`에는 `target="_blank" rel="noopener"`.
- **링크를 지어내지 않는다.** 수집 단계에서 확인한 공고ID만 쓰고, 모르는 건은 링크 없이 두고 그 사실을 적는다.

러너가 로그에서 찾아 쓸 수 있도록, HTML을 쓴 뒤 다음 두 줄을 그대로 출력한다:
```
[HTML] result/latest.html — <바이트수>바이트, 히트 <n>건
[HTML-ARCHIVE] result/archive/<파일명> (직전 회차 보관)
```

## 5. 알림·메일 템플릿

### 알림 (`PushNotification`, 1줄·200자 이내)
```
IRIS 신규 관련공고 2건: ○○기술개발(직접, D-43) 외 1건 — 리포트 생성됨, 메일 초안 확인
```
- 히트 없으면 **보내지 않는다**.
- 실행 자체가 실패했으면 실패를 알린다: `공고 모니터링 실패: IRIS 목록 0건(엔드포인트 변경 의심). 수동 확인 필요`
  **모니터링이 죽은 줄 모르는 것이 최악의 실패다.**

### 메일 (Gmail `create_draft`)
- 수신: 프로파일의 알림 메일주소 (없으면 초안 생성을 건너뛴다)
- 제목: `[공고알림] {YYYY-MM-DD} IRIS 관련공고 {N}건 — {최상위 공고명} 외`
- 본문: 공고별로 (등급 · 공고명 · 마감 D-day · RFP 인용 2~3줄 · 판정 · 원문링크 · 리포트 경로)

> ⚠️ **자동 발송은 대개 불가**: 연결된 Gmail 도구에 `create_draft`만 있고 발송 도구가 없는 구성이 흔하다.
> 초안까지 만들고 사용자가 확인 후 보내는 흐름이 최선이며, 알림에 "메일 초안 생성됨"을 덧붙여 이를 알린다.
> 헤드리스 실행에서는 커넥터 자체가 없을 수 있다 — 이때는 초안을 건너뛰고 리포트 경로만 알린다(실패 아님).

### 확인 리마인더 (선택)
밤에 돌리고 아침에 결과만 보는 흐름이라면, 캘린더에 **다음날 확인 일정**을 만들어 본문에 결과 링크를 넣는다.

**반복 일정으로 만들지 마라.** 지난 회차 결과를 가리키는 일정이 캘린더에 계속 쌓인다.
매 회차가 **지난주 일정을 지우고 이번 주 것 하나만 새로 만드는** 방식이 맞다. 지울 대상 ID는
`calendar_event.json` 같은 상태 파일에 남긴다. 캘린더 도구를 쓸 수 없는 환경이면 `.ics` 파일로
대신 쓰고 그 사실을 로그에 남긴다 — 조용히 넘기지 않는다.

## 6. 상태 파일 스키마

`seen_rfp.json`
```json
{
  "last_run": "2026-08-09T23:10:00+09:00",
  "scope": "IRIS 사업공고 > 접수중 전수 (4회차, 증분 — 신규 3건)",
  "seen": [
    {
      "id": "IRIS-018951",
      "title": "2026년도 ○○ 탐색연구 2차 공고",
      "grade": "탈락(규모 미달) · 무관",
      "reported_at": "2026-08-09",
      "deadline": "2026-09-07",
      "report": null,
      "note": "첨부 RFP 9건 전문 추출·대조. 과제당 90~100백만원/12개월 = 하한 미달. 연구축 어휘 0건"
    }
  ]
}
```
- `id`는 포털 공고번호를 쓴다. 없으면 (공고명 정규화 + 마감일) 해시.
- **`note`에 탈락 근거를 남기는 것이 핵심이다.** 다음 회차에 같은 공고를 다시 열어보지 않게 된다.
- 마감 6개월 경과 항목은 정리해 파일이 무한정 커지지 않게 한다.

## 7. 자동 실행 설정

| 방식 | 가능 여부 | 사유 |
|------|----------|------|
| **OS 스케줄러 → `claude -p`** (Windows 작업 스케줄러/cron) | ✅ 권장 | 로컬 루틴 폴더·커넥터에 전부 접근 가능 |
| 클라우드 스케줄 | ⚠️ 조건부 | IRIS 수집 자체는 HTTP라 가능하다. 다만 루틴 폴더(이력·아카이브)와 커넥터를 어떻게 붙일지 설계가 필요하다 |
| 세션 cron | ❌ | 세션이 살아있는 동안만 유효 |

> 예전 판은 "IRIS가 JS 렌더링이라 클라우드 실행 불가"라고 적었는데 **실측으로 깨진 전제**다.
> 로컬 스케줄러를 쓰는 진짜 이유는 렌더링이 아니라 **상태 파일과 커넥터가 로컬에 있기 때문**이다.

**산출 루트**: 모니터링은 특정 제안서 프로젝트에 속하지 않으므로 **전용 루틴 폴더**를 쓴다
(`profile.md`·`seen_rfp.json`·`result/`·`raw/`·`logs/`·`scripts/`). 역할 대응표는 SKILL.md "출력 위치" 절 참조.
러너 프롬프트에 **폴더 배치를 절대경로로 명시**해야 헤드리스 실행이 헤매지 않는다.

**설치 템플릿**: `assets/routine-scaffold/` — 러너 `.sh`/`.bat`, `profile.md` 템플릿, 스케줄러 등록 절차.
(템플릿이지 동작본이 아니다: 실제로 도는 파일은 각 PC의 루틴 폴더에 있고, 구조가 바뀌는 수정을 했을 때만
템플릿을 함께 갱신한다.)

**놓치기 쉬운 설정** — 기본값 그대로 두면 조용히 안 돈다:
- `StartWhenAvailable` = True — 예약 시각에 PC가 꺼져 있었으면 다음 부팅 후 실행. **주간 작업에는 필수.**
- 배터리 옵션 — 노트북 기본값은 배터리 상태에서 아예 시작하지 않는다.
- `.bat`는 **CRLF**로 저장 (LF면 실행 실패).
- 등록 후 `schtasks /Query /V`로 "다음 실행 시간"을 반드시 확인한다 — 생성 성공 메시지만 믿지 않는다.

**★ 같은 루틴 폴더를 두 PC가 공유하면(클라우드 동기화 폴더) 반드시 소유 PC를 고정한다.**
양쪽에 작업이 등록돼 있으면 같은 시각에 함께 돌아 이력·결과·캘린더 일정을 서로 덮어쓴다.
동기화 폴더는 잠금이 아니므로 `flock`으로는 막을 수 없다 — `owner.txt`에 적힌 호스트명이 아니면
아무것도 하지 않고 빠지는 가드를 러너 맨 앞에 둔다(scaffold의 `.sh`에 구현돼 있다).
이력 파일이 반쪽만 반영되면 다음 주에 이미 본 공고를 신규로 다시 보고하게 된다.

**프롬프트 원칙**: 자동 실행에는 대화 맥락이 없다. 작업 디렉토리·프로파일 경로를 **절대경로로** 박고,
"헤드리스이므로 되묻지 말고, 실패하면 실패 사실을 알려라"를 명시한다.

## 8. 실패 모드

| 증상 | 원인 | 대응 |
|------|------|------|
| 매주 같은 공고 알림 | 이력 미갱신 | ⑦단계 누락 점검. 이력 갱신은 알림 발송과 한 세트다 |
| 두 PC가 결과를 덮어씀 | 동기화 폴더 공유 | §7의 소유 PC 가드 |
| 알림은 오는데 다 무관 | 판정을 제목으로만 함 | ⑤ 첨부 추출이 실패했는지 확인. 잠정 판정은 반드시 표기 |
| 관련 공고를 놓침 | 키워드 검색만 사용 | 포털 검색은 사업명 기준이라 누락된다. 접수중 전수 훑기 |
| 알림이 아예 안 옴 | 실행 실패를 조용히 삼킴 | 실패 자체를 알림으로 보내도록 되어 있는지 확인 |
| HTML이 지난주 것 그대로 | 에이전트가 ⑥-1을 건너뜀 | 러너가 `latest.html` mtime을 실행 시작 시각과 비교해 로그에 남기게 한다 |
| 첨부가 안 열림 | 라이브러리 부재·스캔 PDF | 본문만으로 잠정 판정 + "수동 확인 필요" 명시 |
