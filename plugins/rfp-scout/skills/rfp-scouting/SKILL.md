# 공고 탐색 스킬 (RFP Scouting)

"어디에 낼지"를 정하기 전 단계. 공고 포털을 훑어 **내 연구주제와 관련된 공고만** 걸러낸다.

목표는 많이 긁어오는 게 아니라, **자격이 되고 마감이 남아있고 RFP 본문이 내 주제와 맞는 공고**만 올리는 것이다.

**두 가지 실행 모드**
- **주간 모니터링** (주 1회 자동, 요일·시각은 설치별) — 신규 공고 → RFP 심층 대조 → 관련 건만 알림·메일·리포트. 절차는 아래 "주간 모니터링" 절.
- **온디맨드 탐색** (사용자 요청) — 후보 목록 + 적합도 랭킹 → 사용자 선택.

공통 워크플로우(1~6)를 먼저 따르고, 주간 모니터링은 7절을 추가로 수행한다.

## 동봉 도구

| 도구 | 용도 |
|------|------|
| `scripts/iris_fetch.py` | IRIS 목록·상세·첨부 수집 (표준 라이브러리만, 로그인·브라우저 불필요) |
| `scripts/extract_attachment.py` | 첨부 PDF·HWPX·HWP·ZIP → 텍스트 |
| `references/portal-sources.md` | 포털별 접근 경로·검증 상태·함정 |
| `references/weekly-monitor.md` | 주간 모니터링 상세 절차·리포트/알림 템플릿·상태 파일 스키마 |
| `assets/profile/` | **연구주제·키워드 등록양식** — 사용자가 직접 고치는 유일한 설정 파일(빈 양식 + 작성 예시) |
| `assets/routine-scaffold/` | 주간 자동 실행 루틴 설치 템플릿(러너·소유PC 가드·스케줄러 등록) |

## 워크플로우

### 1. 프로파일 확보
프로파일 파일(기본 `_workspace/00_scout_profile.md`, 루틴 폴더에서는 `profile.md`)을 읽는다. 없으면 사용자에게 물어 생성한다:

| 항목 | 무엇을 적나 | 용도 |
|------|------------|------|
| **내 연구주제 서술 (3~5줄)** | 소속·전공과 핵심 연구축을 (1)…(2)… 로 나열 | **RFP 관련성 의미 판정의 기준** |
| 관심 기술 키워드 | 검색어로 쓸 기술 용어 10~20개 | 검색어 생성 |
| 상위어/유의어 | 상위 개념 5~8개 | 0건일 때 확장 |
| 제외어 | 이름이 비슷하지만 무관한 분야 | 오탐 제거 |
| 소속·자격 | 기관유형(출연연/대학/기업), 주관 가능 여부, 기업참여 매칭 | 하드필터 |
| 규모·기간 하한 | 예: 연 1.2억 이상 / 1년 이상 | 하드필터 |
| 탐색 범위 | 포털·부처 목록, 수집 기준 시점 | 수집 범위 |
| **알림 설정** | 알림 on/off, 수신 메일주소, 최소 보고 등급 | 주간 모니터링 |

**연구주제 서술이 키워드보다 중요하다.** 관련성 판정은 키워드 문자열 매칭이 아니라 의미 대조이기 때문이다.
프로파일은 다음 실행에서 재사용되므로 반드시 파일로 남긴다. 매번 되묻는 것은 실패다.

**등록양식은 `assets/profile/`에 별도로 있다** — 빈 양식 `profile.template.md`, 작성 예시 `profile.example.md`,
설명 `README.md`. 사용자가 이 양식을 복사해 직접 채우는 것이 정상 경로이고, 대화로 만들어 줄 때도 이 양식 구조를 그대로 따른다.

**프로파일을 다루는 규칙 — 사용자 소유 파일이다.**
- 사용자가 쓴 내용을 **임의로 고치지 않는다.** 키워드 추가·제외어 변경·하한 조정은 사용자가 요청했을 때만 하고,
  무엇을 어떻게 바꿨는지 보고한다. 판정이 잘 안 맞는다고 스킬이 몰래 기준을 바꾸면 사용자는 왜 결과가 달라졌는지 알 수 없다.
- 스킬이 자동 갱신하는 곳은 맨 아래 **「실행 이력」 표 하나뿐**이다(최종 탐색 시각·다음 회차 확인 사항).
- 양식에 없는 항목·자유 서술이 있으면 **무시하지 말고 판정 참고자료로 함께 읽는다**
  ("총괄 주관은 부담", "지역 제한 공고는 한 단계 낮춤" 같은 지시가 여기 들어온다).
- 프로파일이 좁아 후보가 0건이면 키워드 확장·범위 확대를 **제안**하고 멈춘다. 임의 확장은 하지 않는다.

### 2. 수집 모드 선택
포털마다 접근성이 다르므로 **모드를 섞어 쓰되, 각 후보 레코드에 출처 모드를 기록**한다.

| 모드 | 수단 | 언제 |
|------|------|------|
| **B. HTTP 직접 호출** (IRIS 기본) | `scripts/iris_fetch.py` — 목록 JSON·상세 HTML·첨부 파일 | IRIS. **로그인·쿠키·브라우저 전부 불필요**(2026-08-12 재실측). 빠르고 헤드리스·클라우드에서도 돈다 |
| **A. 브라우저 자동화** | `playwright` MCP (`browser_navigate` → `browser_snapshot` → `browser_evaluate`) | 정말로 JS·로그인이 필요한 포털. IRIS에는 **필요 없다** |
| **C. 웹검색 폴백** | `WebSearch`, `WebFetch` | A·B 실패·차단 시. 공고명·마감일·원문 링크 최소 3필드만 확보 |
| **D. 오프라인** | 사용자가 준 로컬 공고 파일 폴더를 `Read`/추출 스크립트로 | 시연·재현·네트워크 불가 시. **결정적 결과**가 필요할 때 |

> **모드 A를 기본으로 삼지 마라.** 예전 판은 "IRIS는 JS 렌더링이라 Playwright 필수"라고 적었는데,
> 실측으로 깨진 전제다. 목록·상세·첨부 전 구간이 평범한 HTTP다. 브라우저를 띄우면 느리고,
> 그것 때문에 클라우드·헤드리스 실행이 불가능하다고 잘못 결론 내리게 된다.

포털별 URL·파라미터·추출 대상·알려진 함정은 `references/portal-sources.md`를 읽는다.
셀렉터·엔드포인트는 사이트 개편으로 깨지므로, **깨졌으면 고친 경로를 그 파일에 반영**해 다음 실행이 다시 헤매지 않게 한다.

### 3. 정규화 (수집 직후 즉시)
포털마다 필드명이 다르므로 아래 스키마로 통일한다. 같은 사업이 IRIS와 부처 홈페이지에 중복 게시되는 일이 잦아,
정규화 없이는 중복 제거가 불가능하다.

```
| id | 공고명 | 사업/세부사업 | 공고기관 | 전문기관 | 접수기간 | D-day |
| 총 지원규모 | 과제당 규모 | 연구기간 | 주관자격 | 기업참여 | 과제유형(지정/자유) |
| RFP 수 | 원문URL | 첨부 | 수집모드 | 수집일시 | 신뢰도 |
```

- **중복 제거 키**: (공고명 정규화 + 접수마감일). 중복이면 정보가 더 완전한 레코드를 남기고 다른 URL은 `별칭URL`로 병기한다.
- **신뢰도**: `확인됨`(원문 직접 확인) / `확인필요`(검색 스니펫 기반) / `추정`(계산·추론). 사실처럼 섞지 않는다.
- 확인 못 한 필드는 비우고 `-`로 둔다. 그럴듯한 값을 채우면 하류 전체가 오염된다.
- **공고번호가 나오면 원문 링크를 만들어 함께 적는다.** 번호만 적어 두면 확인할 때마다 포털에서 다시 검색해야 한다.

### 4. 하드필터 (탈락 판정)
아래에 걸리면 **점수 계산 없이 탈락**시키고, 탈락 표에 사유와 함께 남긴다(다음 회차 대비).

- 접수 마감 경과 (D-day < 0)
- 주관연구개발기관 자격 미달 (예: 중소기업 전용, 대학 전용)
- **규모·기간 하한 미달** — 과제당 기준으로 판단한다. 총 사업비가 아니다
- 필수 매칭 불가 (기업 부담금·컨소시엄 필수인데 확보 수단 없음)
- 프로파일 제외어 매칭 / 기술 분야 완전 불일치
- 동일 연구자 중복 수행 제한 저촉

**주관 자격이 없어도 참여기관으로 들어갈 수 있으면 탈락시키지 않는다** — 등급을 `간접관련`으로 내리고 참여 형태를 리포트에 명시한다.

### 5. 적합도 채점 (100점)
살아남은 후보만 채점한다. 각 항목은 **근거 한 줄**을 함께 남긴다 — 점수만 있으면 사용자가 검증할 수 없다.

| 축 | 배점 | 판단 기준 |
|---|---|---|
| 기술 적합도 | 35 | 공고 RFP 요구기술 ↔ 프로파일 연구주제 일치도. 핵심 요구가 우리 주력이면 만점 |
| 수행 역량 정합 | 20 | 보유 인프라·실적·기존 과제와의 연속성. 신규 진입 부담이 크면 감점 |
| 규모·기간 부합 | 15 | 선호 규모·기간 대비. 과소·과대 모두 감점 |
| 경쟁 강도 | 15 | 지정공모(RFP 특정)일수록 낮음, 자유공모·대형 사업일수록 높음. 낮을수록 고득점 |
| 준비 여유 | 15 | D-day 기준. D-30↑ 만점, D-14 미만은 절반 이하 + "촉박" 경고 |

**80점 이상**을 추천 후보로, 60점 미만은 표에는 남기되 추천하지 않는다.

### 6. 보고 및 인계
후보 목록 파일을 쓰고, 사용자에게 상위 3~5건을 요약 보고한 뒤 선택을 받는다.
**임의로 1건을 고르지 않는다** — 과제 선택은 파급이 가장 큰 결정이다. STATUS는 `NEEDS_USER_INPUT`.

사용자가 고르면 그 레코드의 원문URL·**이미 받아 둔 첨부 경로**를 후속 분석 단계에 그대로 넘긴다(재탐색·재다운로드 금지).

### 7. 주간 모니터링 (주 1회 자동)
1~5절을 IRIS 중심으로 수행한 뒤, 아래를 추가한다. 상세 절차·템플릿은 `references/weekly-monitor.md`를 읽는다.

**7-1. 중복 제거** — 보고 이력 파일(`seen_rfp.json`)과 대조해 **이미 보고한 공고는 제외**한다.
매주 같은 공고로 알림이 오면 사용자는 알림 자체를 무시하게 된다.

**7-2. RFP 심층 대조 (핵심)** — 공고 제목만으로 판정하지 않는다.
국가 R&D 공고는 제목이 포괄적이고("○○년도 △△기술개발사업 신규지원 대상과제 공고"),
실제 내용은 **첨부 RFP 문서 안에 수십~수백 개 항목**으로 들어있다.
1. 공고 첨부(HWP/HWPX/PDF/ZIP)를 `raw/`에 다운로드 — `iris_fetch.py download`
2. 텍스트 추출 — `extract_attachment.py` (별도 PDF 추출 스킬이 설치돼 있으면 그것을 써도 된다)
3. **RFP 항목 단위로 분할**한 뒤 프로파일의 연구주제 서술과 의미 대조
4. 3등급 판정:

| 등급 | 기준 | 처리 |
|------|------|------|
| **직접관련** | RFP 요구기술이 내 주력과 일치. 주관·핵심 수행 가능 | 알림 + 메일 + 리포트 |
| **간접관련** | 세부과제·위탁·공동연구로 참여 여지. 인접 기술 | 리포트 (알림은 프로파일 설정에 따름) |
| **무관** | 접점 없음 | 로그에만 기록 |

**판정에는 반드시 RFP 원문 문장을 인용한다.** 요약만 남기면 사후 검증이 불가능하고 없는 내용을 지어낼 여지가 생긴다.

**7-3. 분석리포트 생성** — 직접/간접관련 공고마다 `reports/{YYYYMMDD}_{공고약칭}.md`.
구성: 공고 개요 → **해당 RFP 원문 인용** → 내 주제와의 접점·차별화 가능 지점 → 자격·컨소시엄 요건 →
예산·기간 → D-day와 준비 일정 → 판정(추천/보류)과 근거 → 원문 링크·첨부 로컬 경로.

**7-4. 알림·메일** — 히트가 있을 때만 보낸다. **"이번 주 해당 없음"은 리포트 파일에만 기록**한다(빈 알림은 신뢰를 깎는다).
- 알림: `PushNotification` — 1줄. 예: `IRIS 신규 2건 관련: 에너지기술개발사업(직접관련, D-31) 외 1건`
- 메일: Gmail `create_draft`로 **초안 생성**. ⚠️ 연결된 Gmail 도구에 발송 기능이 없으면 자동 발송은 불가하다.
  초안까지 만들어 두고 알림에 "메일 초안 생성됨"을 덧붙여, 사용자가 확인 후 1회 클릭으로 보내게 한다.
  Gmail 연결이 없는 실행 환경에서는 초안 생성을 건너뛰고 리포트 경로만 알린다(실패로 처리하지 않는다).

**7-5. 이력 갱신** — `seen_rfp.json`에 (공고ID, 공고명, 판정등급, 보고일, 마감일, 판정 사유)를 추가한다.

`STATUS`는 히트가 없으면 `NO_HIT`(정상 종료)이다.

## 출력 위치 — 산출 루트는 고정이 아니다

아래 파일명은 **제안서 작성 파이프라인 안에서 쓸 때의 기본값**(`_workspace/00_*`)이다.
공고 모니터링은 특정 제안서 프로젝트에 속하지 않고 계속 돌아가므로, **전용 루틴 폴더를 산출 루트로 쓰는 편이 자연스럽다.**

산출 루트는 다음 순서로 정한다:
1. 사용자가 지정한 폴더(러너 스크립트 프롬프트나 대화에서 명시) — **최우선**
2. 현재 작업 디렉토리에 프로파일 파일이 이미 있으면 그 위치
3. 둘 다 없으면 `_workspace/`

루트가 바뀌어도 **역할별 파일은 1:1로 대응**시킨다. 이름이 달라도 하는 일은 같다:

| 역할 | 파이프라인 기본 | 루틴 폴더 예 |
|------|----------------|--------------|
| 프로파일 | `_workspace/00_scout_profile.md` | `profile.md` |
| 보고 이력 | `_workspace/00_seen_rfp.json` | `seen_rfp.json` |
| 후보 목록 | `_workspace/00_rfp_candidates.md` | `result/latest_candidates.md` |
| 분석리포트 | `_workspace/00_rfp_reports/` | `result/reports/` |
| 원문 사본 | `_workspace/00_rfp_raw/` | `raw/` |

**리포트 안의 경로는 산출 루트 기준 상대경로로 적는다.** 폴더를 옮겨도 링크가 깨지지 않아야 하기 때문이다.

루틴 폴더를 새로 만들 때의 폴더 구조·러너·스케줄러 설정은 `assets/routine-scaffold/`에 템플릿으로 있다.

## 출력

후보 목록 파일 구성:
```
## STATUS: NEEDS_USER_INPUT
## 탐색일시 / 프로파일 버전 / 커버한 포털 (성공·실패 명시)

1. 추천 후보 (점수순) — 정규화 표 + 축별 점수 + 근거 + 추천 사유 3줄
2. 기타 후보 (60~79점)
3. 탈락 목록 — 공고명 · 탈락사유 · 원문 링크
4. 탐색 로그 — 포털별 접근 모드·결과 건수·실패 사유
```

프로파일 파일 — 위 1절 표 + 최종 탐색 시각(증분 탐색 기준점).

주간 모니터링 추가 산출물:
- `reports/{YYYYMMDD}_{공고약칭}.md` — 관련 판정 공고별 분석리포트
- `raw/` — 다운로드한 공고문·첨부 원본
- `seen_rfp.json` — 보고 이력(중복 알림 방지)

## 증분 탐색 (재실행 시)
후보 목록·보고 이력이 있으면 전체를 다시 훑지 않는다:
1. 기존 후보의 D-day를 오늘 기준으로 재계산 → 마감 경과분은 탈락 표로 이동
2. 마지막 탐색 시각 이후 **신규 게시분만** 수집
3. 프로파일이 바뀌었으면 추가된 키워드에 대해서만 전체 범위 탐색

전체 재탐색은 사용자가 "처음부터 다시" 류로 명시할 때만 한다. 이유: 포털 조회는 느리고, 대부분의 재실행 목적은 "새 공고 있나"이다.

**접수중 전체가 20~30건 수준이면 전수 훑기가 키워드 검색보다 안전하다.** 포털 검색은 대개 사업명 기준이라
기술 키워드로 검색하면 실제로 존재하는 공고가 0건으로 나온다.

## 원칙
- **자격 미달 공고를 상위에 올리는 것이 가장 큰 실패다.** 화려한 적합도보다 하드필터가 우선한다.
- **출처 URL 없는 후보는 후보가 아니다.** 사용자가 원문을 열어 확인할 수 있어야 한다.
- **마감일은 항상 원문 기준.** 검색 스니펫의 날짜는 게시일과 마감일이 섞이므로 `확인필요`로 강등한다.
- 포털 접근 실패를 숨기지 않는다. "커버한 포털"에 실패를 명시해야 사용자가 수동 보완할 수 있다.
- **애매하면 간접관련으로 올린다.** 누락이 오탐보다 비싸다 — 놓친 공고는 다음 해까지 기다려야 한다.

## 재현성 (시연·제출물용)
탐색은 실행 시점에 따라 결과가 달라지므로, 재현이 필요하면 다음을 남긴다:
- 탐색 시각·프로파일 파일을 결과에 함께 기록(위 출력 헤더)
- 수집한 공고 원문·첨부를 `raw/`에 저장 → 모드 D로 동일 입력 재실행 가능
- 시연 시에는 모드 D(로컬 스냅샷)로 돌리면 네트워크 상태와 무관하게 같은 결과가 재현된다

## 테스트 시나리오
- **주간 히트**: 예약 시각 자동 실행 → IRIS 신규 5건 → 이력 대조로 3건 신규 → 첨부 RFP 추출 → 1건 직접관련·1건 간접관련 판정 → 리포트 2건 생성 → 알림 1줄 + 메일 초안 → 이력 갱신
- **주간 무히트**: 신규 2건 모두 무관 → `STATUS: NO_HIT`, **알림 미발송**, 리포트에만 "이번 주 해당 없음" 기록
- **첨부 추출 실패**: HWP 파싱 실패 → 공고 본문만으로 잠정 판정 → 리포트 최상단에 "RFP 원문 미확인 — 수동 확인 필요" 명시 → `PARTIAL`
- **규모 미달**: 신규 3건이 전부 과제당 1억/12개월 → 하드필터 탈락. 그래도 첨부는 열어 확인 사살하고 사유를 이력에 남긴다
- **정상(온디맨드)**: 프로파일 없음 → 관심분야 질의 → 프로파일 생성 → 포털 탐색 → 12건 수집 → 하드필터 5건 탈락 → 7건 채점 → 상위 3건 보고 → 사용자 선택
- **포털 실패**: 엔드포인트 개편으로 목록 0건 → 웹검색 폴백으로 공고명·마감일만 확보(`확인필요`) → STATUS `PARTIAL` + 수동 확인 요청 + `portal-sources.md` 갱신
- **증분**: 1주 후 재실행 → 기존 7건 중 2건 마감 경과 → 탈락 이동 → 신규 3건만 추가 수집 → 갱신 보고
