## 5. 쪽수·열림 검증

**한컴 COM이 정답**이다 — `HWPFrame.HwpObject` → `Open(..., "forceopen:true")` → `PageCount`.
WSL에서는 `powershell.exe -File <ps1>`, 파일은 **Windows 경로**에 둘 것. Open 성공 = 한글 열림 검증 동시 달성.

```powershell
$hwp = New-Object -ComObject HWPFrame.HwpObject
$hwp.RegisterModule("FilePathCheckDLL","FilePathCheckerModule")
$null = $hwp.Open("C:\...\chk.hwpx","","forceopen:true")
Write-Output ("PAGECOUNT=" + $hwp.PageCount)
$hwp.Clear(1); $hwp.Quit()
```

⚠️ **PageCount는 평가위원이 직접 측정할 수 없는 유일한 항목**이면서 형식 축 감점의 **80.6%**를 차지한다.
규율 J-6에 따라 위원은 이를 「PASS」로 위장하지 말고 **"COM 보고값 수용"**으로 표기해야 한다.
→ **2026-08-14부터는 `scripts/gate_pages.py` 가 결과 JSON(`50_gate_pages.json`)을 남기므로 위원은 그 값을 인용한다.**

### ★★ 쪽수 측정의 함정 2건 (둘 다 「에러 없이 틀린 값」을 준다 — 2026-08-14 실측)

**⑴ 잔류 Hwp 인스턴스 때문에 같은 파일이 9p / 11p 로 번갈아 측정된다.**
`Quit()` 뒤에도 **창 없는 Hwp 프로세스가 남고**, 다음 `New-Object HWPFrame.HwpObject` 가 ROT 에 등록된
그 인스턴스에 붙는다. 인스턴스마다 조판 상태가 달라 **쪽수가 교대로 바뀐다**(11·9·11·9 로 4회 재현).
→ 측정 전에 **`MainWindowTitle` 이 빈 Hwp 프로세스만** 정리한다. **창이 있는 인스턴스는 절대 죽이지 말 것**(사용자 문서).
정리 후 4회 연속 동일값(11p)으로 수렴했다. **9p 는 오염된 인스턴스가 준 거짓 통과였다.**

**⑵ PowerShell 5.1 은 BOM 없는 `.ps1` 을 ANSI(cp949)로 읽는다.**
파이썬이 UTF-8로 쓴 스크립트에 **한글 주석**이 있으면 바이트가 깨지면서 **뒤따르는 줄이 문자열로 먹혀**
`Write-Output ("PAGECOUNT=" + …)` 한 줄이 **통째로 사라졌다**(에러 없음, 뒤의 `SAVED=True` 만 출력).
→ `.ps1` 은 반드시 **`encoding="utf-8-sig"`(BOM)** 로 쓴다. 또는 스크립트를 ASCII 로만 작성한다.

**⑶ 같은 파일이 9p / 12p 로 갈린다 — 한글이 문서의 줄간격을 안 지킬 때가 있다.**
PDF 실측으로 원인을 확정했다: 본문 줄 간격이 **17.5pt(문서 지정 160% × 11pt)** 인 회차와
**22.8pt(글꼴 메트릭 기준 ≈207%)** 인 회차가 번갈아 나온다. 여백·글꼴·본문은 동일하다.
→ 게이트는 **PDF 에서 줄간격을 실측해 규격(±15%)과 맞는 회차만 채택**한다(`gate_pages.py`).
규격 회차를 못 얻으면 최악값으로 판정하고 사유를 남긴다. **이 판정 없이 최대값만 쓰면 30% 과대 측정**이 된다.

★ **그 FAIL 은 문서 결함이 아닐 수 있다 — 감축하기 전에 재측정한다**(2026-08-15 실측 2건).

| 파일 | 오염 회차 판정 | 재측정 판정 |
|---|---|---|
| `c1/33_proposal.hwpx` | 22.78pt · **13p FAIL**(0·1·2·3장 전부 초과) | 17.5pt · **9p PASS**(위반 0·경고 1) |
| `c2/33_proposal.hwpx` | 22.78pt · **11p FAIL**(1·4장 초과) | 17.6pt · **9p PASS** |

**같은 원고인데 판정이 뒤집힌다.** 두 건 모두 `--repeat 3` 을 다 쓰고도 규격 회차를 못 얻었고,
곧바로 같은 명령을 다시 돌리자 첫 회차에서 규격 조판이 나왔다 — **드문 사고가 아니라 상시 재발**이다.
그래서 게이트는 이 상태를 결과 JSON에 `"measurement_suspect": true` 로 표시하고 재측정을 먼저 안내한다.
이 표시가 붙은 FAIL 을 근거로 원고를 깎으면 **멀쩡한 문서를 훼손**한다.

| note | 읽는 법 | 할 일 |
|---|---|---|
| `줄간격 실측 17.5pt (규격 17.6pt) — 규격 조판 회차 채택` | 신뢰 가능한 실측 | 판정 그대로 수용 |
| `⚠️ 규격 줄간격…으로 조판된 회차 없음 … 최악값 Np 로 판정` | **측정 오염 의심** | Hwp 프로세스 전부 종료 후 재측정 → 그래도 같으면 감축 |
⚠️ `lineSpacing` 을 `type="FIXED"` 로 바꾸면 조판은 결정적이 되지만(5/5 동일) 제목·표까지 같은 높이로 눌려
**9p → 7p 로 문서가 뭉개진다.** 값 단위도 직관과 달라 **`value = pt × 200`**(17.6pt → 3520)이다. 권장하지 않는다.

**장별 분량은 PDF 로 잰다.** `SaveAs(path,"PDF","")`(인수 3개 — 2개면 오버로드 없음 오류) 로 저장한 뒤
PyMuPDF 로 **장 제목의 시작 쪽 + 쪽 안 세로 위치**를 읽어 점유량을 소수 쪽 단위로 계산한다.
쪽 단위 정수로만 세면 경계 쪽 때문에 ±1p 오차가 나 「2p 배분에 2.1p」 같은 판정을 못 한다.

## 6. 기타 환경

- **WSL에서 Windows·클라우드 동기화 폴더를 편집할 때 간헐 EACCES** → python 직접 쓰기로 우회.
- **HWP(구형 바이너리) 읽기**: WSL에 hwp5txt·LibreOffice가 없으면 `olefile`+`zlib(-15)`+레코드 파싱
  (`tag=h&0x3FF`, `size=(h>>20)&0xFFF`, `HWPTAG_PARA_TEXT=67`, UTF-16LE) 자체 파서가 유일 경로.
- **선행조건**
  - **Node.js 18+** — 조립 도구 kordoc이 `npx` 로 돈다. 최초 1회는 패키지 내려받느라 느리고 **네트워크가 필요**하다.
  - `pip install --user --break-system-packages olefile` — 구형 `.hwp` 공고문을 읽을 때만.
    (WSL python3는 PEP 668이라 `--break-system-packages` 필수, venv는 ensurepip 부재로 실패)
  - 게이트 스크립트 2종(`gate_hwpx.py`·`gate_regress.py`)은 **표준 라이브러리만** 쓴다 — 추가 설치 불필요.
